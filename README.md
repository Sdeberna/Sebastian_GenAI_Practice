# Inline Email Assistant

A small Wizard-of-Oz class prototype demonstrating prepared email suggestions inside a reply-writing experience, with explicit user review and control.

## First working slice

Read Alex's sample email asking about Thursday at 2 PM. Choose a listed example instruction or type it, then click **Write with AI**, attached to the instruction field.

- **Accept:** insert the suggestion, including edits, into an editable draft. A visible **“Added to your draft”** confirmation appears.
- **Accept & replace draft:** explicitly replace an existing draft and show the same confirmation.
- **Edit:** modify the suggestion before accepting; empty suggestions cannot be accepted.
- **Regenerate:** cycle between two prepared alternatives for that scenario. Manual edits are not discarded until the user chooses **Discard edits & regenerate**; **Keep my edits** preserves them.
- **Cancel:** restore the instruction without changing the accepted draft.
- **New AI instruction:** repeat without reloading while keeping the accepted draft editable.
- **Unsupported request:** stay at the instruction field, show an inline scope notice, and offer **Edit instruction** or **Continue manually**. Manual editing opens a blank draft if none exists, or preserves the existing draft.

This prototype never sends email. Refreshing clears the session's work.

## Open and use

**In Replit:** Open the **Inline Email Assistant** preview and start its existing web workflow if stopped. No credentials, backend, or database are required. The revision results below refer to this development preview, not a newly published production version.

Supported example instructions:

1. **Scheduling:** “Decline Thursday and propose Friday after 3 PM”
2. **Scheduling alternate:** “Politely decline Thursday at 2 PM and suggest Friday after 3 PM instead”
3. **Friendly class conflict:** “Make it nicer but not too formal and explain that I have a class”

Each has a **Use example** control beside the instruction field. All demonstrate declining Thursday at 2 PM and proposing Friday after 3 PM; the third adds the class explanation and friendly wording.

**Outside Replit:** With Node.js 24 and pnpm 10 installed, run from the repository root:

```sh
pnpm install
PORT=5173 BASE_PATH=/ pnpm --filter @workspace/inline-email-assistant run dev
```

Open `http://localhost:5173/`.

## Simulated AI

**Responses are simulated/prepared, not generated by a live AI model.** The implementation matches an explicit list of authored example instructions, ignoring case, repeated whitespace, and final `.`, `!`, or `?` punctuation. It does not infer meaning, detect intent semantically, or understand custom scheduling requests. A near-match with extra instructions is unsupported, even if it contains a listed phrase.

Two authored reply alternatives exist per scenario. Unknown instructions do not fall back to a decline. A persistent simulation badge, a scope explanation near the field, and a prepared-response notice on each suggestion disclose this behavior. No live AI service, hidden human operator, calendar, Gmail, accounts, database, or external response-generation API is involved.

# Project Prototype Revision

## 1. Priority Improvements

1. **Prevent misleading opposite-meaning replies.** Replace the earlier keyword/default-response behavior with a conservative supported-example check. Unsupported requests produce an inline notice and recovery choices, not a confidently presented decline.
2. **Confirm successful acceptance visibly.** Both acceptance actions now show “Added to your draft. You can keep editing below.” The confirmation clears when the user starts editing or begins a new instruction.
3. **Explain scope before generation.** Put the supported scenarios, selectable full examples, and exact-example matching limitation beside the field. Retain the simulation badge and add a one-line prepared-response reminder on suggestions.

## 4. Before-and-After Comparison

**Same input:** “Say yes, Thursday at 2 PM works for me”

| Earlier prototype — observed before revision | Revised prototype — observed after revision |
| --- | --- |
| Clicking Write with AI showed: “Thursday at 2 PM doesn't work for me. Would Friday after 3 PM work instead?” This contradicted the user's instruction because all non-class instructions defaulted to the decline scenario. | Clicking Write with AI showed: “This prepared-response prototype does not support that instruction.” It explained the two supported scenarios and offered Edit instruction or Continue manually. No decline suggestion or Accept action was shown, and the draft was unchanged. |

The earlier behavior was reproduced in Chromium before changing the implementation; the revised behavior was exercised in the risk test afterward. Neither comparison sent an email.

## 5. Evidence Interpretation

The observations support a narrow conclusion: the implemented example flows, visible success feedback, edit controls, and unsupported-request safeguard worked in the tested Chromium interactions. They do not prove that first-time users understand every label, that all browsers behave identically, or that arbitrary instructions are understood. The two typical instructions intentionally map to the same scheduling scenario; the challenge is a separate prepared scenario. The risk test shows rejection of specific mismatches, not an intelligent intent classifier. A grade or “Excellent” rating remains the evaluator's decision.

## 6. One Concrete Risk: Sending the Opposite Meaning

**Risk:** A user asks to accept Thursday but trusts a polished decline that appears to answer the instruction. Copying that reply into a real email could create a scheduling error or undermine trust. This prototype itself has no send action.

**Safeguard:** Only listed examples can produce prepared suggestions. An unlisted instruction, including the exact “Say yes…” input or an added custom schedule, cannot reach a valid-looking prepared response through generation. The inline notice explicitly explains the limitation and offers manual recovery without changing the draft. This is conservative text matching, not model understanding or a semantic safety guarantee.

**Human control retained:** Supported replies still require review and explicit Accept; Edit and Cancel remain available, and Regenerate warns before discarding edits. The prepared-response reminder states what the response will do. The user may write a different meaning manually. Future changes to supported examples must keep this fail-closed boundary and re-run the risk case.

## 7. Remaining Limitations and Next Priorities

### Remaining Limitations

1. **Intentionally narrow matching:** only three listed instructions cover two scenarios. Even sensible unlisted paraphrases, negations, languages, or custom requests are rejected. No availability, calendar, or semantic checks occur.
2. **Session-only state and explicit replacement:** refreshing loses work; accepting a later suggestion replaces rather than intelligently revises the existing draft.
3. **Isolated demonstration and limited evidence:** no sending, Gmail, calendar access, or system-wide text assistance; browser assertions are not a peer usability study or a cross-browser accessibility audit.

### Next Priorities

1. **Evaluate comprehension with first-time users:** ask whether they can identify the supported scope, notice acceptance feedback, and recover from the “Say yes…” risk case. Record observed confusion rather than inventing participant results.
2. **Extend boundary and accessibility checks:** test more unsupported paraphrases, keyboard-only recovery, and other browsers before expanding the curated examples.
3. **Scope future capabilities separately:** arbitrary custom requests and calendar integration remain **deferred**, not implemented or promised for this revision. Investigate needs, consent, and feasibility before proposing any integrations; retain the manual path meanwhile.
